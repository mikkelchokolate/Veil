# Veil Panel v0.6 Design

## Goal

Turn the Panel from a feature-complete single-host control plane into an
operationally mature service with explicit first-run setup, durable sessions,
structured audit history, automated disaster recovery, live validation,
privilege separation, a contract-tested API, and a localized accessible UI.

The release must preserve existing state files, CLI commands, API token
authentication, managed runtime layouts, and loopback development workflows.

## Release Shape

All work is delivered through one release branch and one pull request. The
implementation is split into independently testable commits:

1. Refresh the roadmap and documentation after v0.5.0.
2. Introduce shared exposure and TLS policy.
3. Add a loopback-only first-run setup flow.
4. Replace the process-global session map with a durable session store.
5. Add structured Panel audit events and retention.
6. Add scheduled encrypted backups, retention, verification, and restore jobs.
7. Add real-time validation and richer apply previews.
8. Move root operations behind a narrow privileged helper.
9. Complete OpenAPI contracts and generate a Go client.
10. Add English/Russian localization and accessibility/mobile verification.

New proxy protocols are outside this release. Reliability and security take
priority over expanding the managed runtime catalog.

## Exposure Policy

A single `ExposurePolicy` evaluates the effective Panel mode, listener, TLS
source, API token, session users, metrics policy, and explicit unsafe flags
before a socket is opened.

The supported modes are:

| Mode | Panel listener | TLS | Startup requirements |
| --- | --- | --- | --- |
| `local` | loopback | optional or self-signed | setup may be incomplete |
| `caddy` | loopback | terminated by Caddy | at least one admin user before Caddy exposure |
| `direct` | non-loopback | native TLS | API token, admin user, authenticated metrics |

Plain HTTP on a non-loopback listener is rejected. A manual deployment may
override this only with an explicitly named unsafe flag and environment
variable. The installer never enables that override.

Direct self-signed TLS remains supported because it is an existing documented
mode, but the server and UI expose a persistent warning. Caddy with a valid
certificate is the recommended public mode.

`/healthz` returns only coarse readiness. `/metrics` follows its independent
policy and cannot be public when the effective exposure is public, including a
loopback listener intentionally exposed through Caddy.

## First-Run Setup

Setup routes exist only when all of these conditions are true:

- no users exist;
- the effective Panel mode is `local`;
- the listener is loopback;
- the request is received through the local Panel listener.

The setup flow creates the first admin, confirms the exposure choice, records
backup preferences, and marks setup complete in Management state. It never
accepts API token rotation or privileged host changes.

`caddy` and `direct` startup require setup to be completed beforehand through
`veil admin set`, `veil admin reset`, or a prior local setup. This prevents an
unauthenticated setup page from becoming publicly reachable through a reverse
proxy.

Setup completion is atomic: password hashing, user creation, settings update,
and state persistence either all succeed or leave the state unchanged.

## Durable Sessions

Browser sessions move from the process-global map to a `SessionStore`
interface. The production implementation uses an atomic JSON store under
`/var/lib/veil/sessions.json`; tests use an in-memory implementation.

Only hashes of the session token and CSRF token are stored. Each record has:

- stable session ID;
- username and issued role;
- creation and last-seen timestamps;
- idle and absolute expiry timestamps;
- user-agent summary and remote address for operator audit.

The default idle timeout is 30 minutes and the absolute timeout is 24 hours.
Last-seen persistence is throttled to avoid a disk write on every request.

Changing a password or role revokes all sessions for that user. Deleting a user
does the same. An administrator may revoke one session, all sessions for one
user, or all sessions except the current session.

## Audit History

Panel security and mutation events use the existing audit package through a new
structured `Recorder` interface. Records are JSONL and contain timestamp,
request ID, actor, role, action, outcome, remote address, target, and sanitized
detail.

Required events include:

- login success and failure;
- logout, expiry, and session revocation;
- user create, update, and delete;
- API token rotation acknowledgement;
- setup completion;
- apply plan, stage, promote, rollback, and service action;
- backup create, verify, restore, prune, and key rotation;
- update attempts.

Secrets, cookies, bearer tokens, passwords, complete client links, and generated
configuration bodies are never recorded.

Audit files rotate by size and retain a configurable number of generations.
The Panel exposes an admin-only paginated read endpoint.

## Backup And Disaster Recovery

The existing encrypted archive remains the interchange format. The archive
manifest gains an explicit format version, Veil version, creation timestamp,
checksums, and source platform metadata.

New operations are:

- `veil backup verify`;
- `veil backup prune`;
- `veil backup schedule`;
- `veil backup restore --check-only`;
- Panel create/list/download/verify/prune controls;
- queued restore jobs with typed confirmation and mandatory recent
  re-authentication.

Scheduling uses shipped systemd service/timer units. Retention supports daily,
weekly, and monthly buckets. Restore validates the archive and version
compatibility before touching live files, creates a safety backup, atomically
replaces state and key files, repairs managed material, and restarts the Panel.

CI keeps compatibility fixtures for the oldest supported archive format and
performs a create/restore test across release versions.

## Live Validation And Apply Preview

Validation is available independently of persistence through dedicated API
routes. Inbound validation checks:

- duplicate protocol/transport bindings;
- live TCP and UDP port availability;
- reserved Panel and helper ports;
- required domain, email, certificate, and credentials;
- DNS reachability where applicable;
- runtime binary and systemd unit availability.

The UI debounces validation while fields are edited and renders field-level
errors plus remediation text. Server-side save and apply validation remains
authoritative.

Apply preview remains secret-free. It adds operation type, source and
destination paths, affected units, interruption risk, validation provenance,
and rollback availability. Configuration bodies and credentials are not sent
to the browser.

## Privileged Helper

The HTTP Panel runs as the dedicated `veil` user. A separate root helper has no
network listener and accepts allowlisted requests through
`/run/veil/helper.sock`.

The helper verifies Unix peer credentials and supports only typed operations:

- promote already validated staged files into managed paths;
- run allowlisted systemd actions for managed units;
- read bounded journald output for managed units;
- apply generated firewall material;
- create, verify, prune, and restore backups;
- rotate the state key;
- stage an update and restart the Panel.

Arbitrary command execution, arbitrary paths, shell strings, and caller-supplied
unit names are rejected. Path operations resolve and verify that source and
destination remain inside configured managed roots.

For tests and non-Linux development, the same interface has an in-process
adapter. Production packages enable the helper socket and do not grant the
Panel process root capabilities.

## API Contract

Every route in `docs/openapi.yaml` has request, success, and error schemas plus
examples. Authentication documents API token, session cookie, CSRF, setup
state, and admin/viewer authorization.

All errors use:

```json
{
  "error": {
    "code": "stable_machine_code",
    "message": "operator-readable message",
    "requestId": "request identifier",
    "details": {}
  }
}
```

Compatibility endpoints may retain their existing top-level `error` string
during v0.6 while also returning the structured object.

CI lints OpenAPI, checks that registered routes are documented, and regenerates
a committed Go client under `sdk/go/veilclient`. Generated output must be clean
after `go generate`.

## Localization And Accessibility

The Panel ships English and Russian catalogs. Locale resolution order is:

1. authenticated user preference;
2. `veil_locale` cookie;
3. `Accept-Language`;
4. English.

Visible UI strings use stable translation keys. API error codes remain
language-neutral; API messages remain English for automation stability.

Interactive controls have labels, keyboard focus states, sensible tab order,
and live regions for asynchronous results. Tables remain scrollable and forms
remain usable at 360 CSS pixels. CI checks rendered HTML semantics, while final
verification uses desktop and mobile browser screenshots.

## Migration And Compatibility

- Existing Management state without setup metadata is considered complete when
  it contains at least one admin.
- Existing sessions disappear once during the upgrade because they were never
  persisted.
- Existing API token clients continue to work.
- Existing backup archives remain restorable.
- Existing root-run development commands use the in-process privileged adapter
  only when explicitly selected or when the helper is unavailable in dev mode.
- Package upgrades create the `veil` user, install helper units, migrate file
  ownership, and leave a safety backup before changing permissions.

## Test Strategy

Each behavior is introduced test-first.

- Unit tests cover policy decisions, session expiry/revocation, audit
  redaction/rotation, retention selection, helper allowlists, translations, and
  error schemas.
- HTTP integration tests cover setup, login, RBAC, CSRF, audit reads, validation,
  backup jobs, and structured errors.
- E2E tests launch real Panel and helper processes over TCP and Unix sockets.
- Packaging tests assert users, permissions, capabilities, read/write paths,
  and systemd sandbox settings.
- OpenAPI contract tests compare registered routes and generated clients.
- Browser verification covers login, setup, users, validation, apply preview,
  backup controls, English/Russian switching, keyboard use, and mobile layout.

## Completion Criteria

The release is complete when all planned routes and commands are documented,
unit/integration/E2E/package tests pass, the generated client is clean, browser
verification passes at desktop and mobile sizes, the single release PR is
merged, its branch is deleted, and the release notes describe migration and
safe exposure modes.
